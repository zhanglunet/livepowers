# 与 PRD-112 的边界：会话内分工 vs 专家编排

PRD-256/T4（trend #1283）。本仓同时存在两套多代理协作形态，本页划清边界、给选用指引、纠正常见误用。
两套都是"主会话派活给别人做"的模板，**没有运行器、不注册为技能**；差别在并行范围与基础设施重量。

## 1. 边界表

| 维度 | PRD-112 并行专家编排（`templates/parallel-experts/`） | PRD-256 会话内分工（本模板包） |
|---|---|---|
| 定位 | 专家 agent 编排，**基础设施级** | pi 会话内轻量分工，**零基础设施** |
| 并行范围 | **跨会话**：同轮派发多位只读专家，产物落盘合并 | **单会话内**：主会话在当前会话里逐个派发子代理 |
| 编排主体 | `orchestrator.md` 四阶段（detect→dispatch→synthesize→write） | 主会话本人（按 `roles/` 三角色页派发与验收） |
| 基础设施 | `orchestra.yaml` + `envelope.md` + specialist/writer 骨架 + finding/report schema + `scripts/gen_harness.py` 生成 harness 目录 | 一份 `handoff.schema.json`（handoff-v1 合同）+ 三角色 Markdown 页，无调度器无目录产物 |
| 合同与合并 | 专家回 finding（schema 校验），编排者按 id 去重合并、保留更高严重度 | 子代理回 handoff `result`（status: done/blocked/rejected + evidence），主会话对照汇总 |
| 写入控制 | **唯一写入者** + 人工 `confirm-write` 门后才派发写入者 | 无独立写入者角色：implement 直接改，verify 只验收不修 |
| 打回流转 | 编排者 synthesize 阶段合并去重，不设 verify 打回 | verify 打回 `rejected` → implement 修复 → 主会话**重派新合同**（引用原 task_id） |

一句话：**112 是"一组专家围绕一个编排在多个会话里并行作业"，256 是"主会话在一轮对话里分三步把活派出去"**。

## 2. 选用指引

- 选 **112**：需要**跨会话持久**协作（编排状态与产物要落盘、可被后续会话接续）；需要**多专家并行**（同轮多位只读专家分头侦察再合并）；涉及有写风险的变更（要唯一写入者 + `confirm-write` 人工门）。
- 选 **256**：**单会话内**一次任务的三角色分工（探索→实现→验证）；要轻——一份 handoff 合同就能派发，不需要任何目录/配置/生成器；主会话要亲自验收每份 `result` 并汇总。
- **两者可组合**：256 的 `implement` 角色可以由 112 专家承担——主会话先把探索合同收拢（256 explore），再把实现任务包进 112 的 `envelope.md` 派给 specialist/writer（跨会话、并行、有写入门），最后回到 256 的 verify 角色做独立验收。组合时合同各自独立：handoff-v1 不进 finding schema，反之亦然。

## 3. 常见误用纠正

**误用一：把 256 当跨会话编排器。**
症状：期望 handoff 合同跨会话持久、几位子代理自动同轮并行、产物由"系统"合并落盘。
纠正：256 没有调度器、编排者和合并规则，派发与验收都是**主会话在当前会话里手工完成**，会话结束合同即止。要跨会话持久 / 多专家并行 / 落盘合并，用 112（`orchestra.yaml` 定义阶段与合并规则，`gen_harness.py` 铺骨架）。

**误用二：为单会话小任务铺 112 全套基础设施。**
症状：一次"侦察一个函数 → 改三行 → 跑个测试"也生成 harness 目录、写 orchestra.yaml、派 envelope。
纠正：成本倒挂。112 的价值在多专家并行与唯一写入者/写入门；单会话三步活用 256——三份 handoff 合同、主会话汇总，零基础设施。判断口诀：**跨会话或多位专家才值得 112；会话内三角色 256 起步**。
