# 本体演进

**本体无需一次覆盖整家企业。**已有定义先复用，缺失定义在任务中补齐，冲突规则由业务责任人裁定并记录依据。一次会话里的临时理解，经确认后才成为工具、Skill 与界面共同引用的业务语义。

## 两层与放置规则

- **参考本体**（领域公理：对象、关系、状态含义、不可违反的约束）——跨客户共享，变化慢。
- **本体孪生**（映射到具体库表、接口、当前状态、可调用行动）——随客户与运行变化。
- **知识放哪里看变化率：**长期稳定的放参考本体；随客户变的放客户扩展；频繁调整的放运行配置（参数）；规则正文放带版本的规则文件，不要写死在代码或提示词里。

## 四个状态

| 状态 | 含义 | 进入条件 |
|---|---|---|
| `candidate` 候选 | Agent 在任务中提出的对象 / 规则 / 口径 | 写明来源（制度、接口、样例、用户说法） |
| `validated` 已校验 | 用真实记录、制度文本、案例核对过 | 附核对证据；冲突已列出 |
| `confirmed` 已确认 | 有权主体确认了业务含义 | 记录确认人、依据 |
| `published` 已发布 | 进入某个本体版本，可被引用 | 版本号、生效时间、迁移说明 |

只有 `published` 的定义可以被已注册能力引用；已发布的任务绑定明确版本。

## 步骤

1. **提出 Delta。**用 `templates/ontology-delta.yaml`：变更类型（新增 / 修改 / 废弃）、对象、定义、来源、适用范围、**生效时间**、是否需要**重算历史结果**、受影响的已注册能力。
2. **分大小两条通道。**
   - 小调整（新增术语、补充说明、新增可选属性）：轻量评审，次版本号。
   - 大调整（对象、关系、状态结构、口径含义变化）：完整评审 + 迁移 + 回归，主版本号。
3. **校验。**用数据、制度、真实案例核对；把"对申请方有利"和"不利"的证据都列上。
4. **确认。**由业务责任人裁定；同名不同义的指标保留独立标识，不要强行合并（例："签约收入"与"确认收入"）。
5. **发布。**写入 `ontology.yaml`，升 `ontology_version`，提交 git；在晨报中列出受影响能力，由 `nightly-crystallization-review` 安排复验。
6. **差异管理。**区分 领域共性 / 客户扩展 / 运行配置。有推广价值的客户扩展，经脱敏、兼容性检查、重新验证后，才能进入公共参考本体（走 `fde-delivery` 的资产四道门）。

## 规则频繁更新的场景

当规则本身定期调整（政策、分组方案、费率表）：

- 规则带版本与生效时间；同一时刻可能有多个版本并存（按业务发生时间选版本）。
- 新规则先由领域人员解释，再用脱敏历史样本、边界案例、专家复核验证，然后按生效时间发布。
- 每个判定结论记录：用了哪版规则、哪些事实触发了哪项检查、谁复核。
- 可以用"正向判定 + 反向校验"双向互证：一个引擎给出结论，另一个按本体检查证据链是否支撑该结论，不一致即输出疑点。

## 红线

- Agent 可以**提出**本体修订，正式业务规则的变更必须获得授权。
- 不在会话里"悄悄"改口径。
- 客户数据、凭证、专有制度不进入公共参考本体。
