# PRD：活软件的"生长面"——次抛展示与语义生成固化结构

> 状态：M1–M3 已实现（#21） · 起草日期：2026-10-08 · 相关：`docs/paradigm.md`、`crystallize-to-system1`、`ontology-evolution`、`ontology-grounded-spec`

## 1. 背景与问题

"活软件"不只是一组固定展示页，页面上还要有一个智能体，具备两种能力：

1. **次抛型的一次性分析展示**：用户临时提一个问题，智能体当场给出分析与图表，用完即弃。
2. **语义生成代码**：智能体把用户的语义需求，指挥模型写成代码，产出原固化表结构里没有的**递进的、不同维度的新结构**（新的派生表、视图、指标与图表）。生成后经验收，**固化进表结构**，成为新的固化表结构与固定展示页。

"活"的含义在第 2 点：**可生长**。次抛不算生长；能用语义长出新的固化结构才算。长出来的东西仍然是固化的，因为固化结构是"计算器结构"：结果按公式由 CPU 算出来，准确、快、便宜，而不是每次由模型"想"出来。

### 与通用 Agent 的区别

通用 Agent（包括网页版的大模型产品）已经能做次抛展示，业界也有 A2UI 这类"智能体用数据描述界面、宿主用自有组件渲染"的开放协议。本 PRD 的定位不同：

- **面向某个具体业务**，而不是通用对话。
- 同时承载三类需求：**大量存量固化需求 + 持续新增的固化需求 + 次抛需求**。
- 对**准确性、安全性、确定性**的要求高得多：数字必须可追溯到确定性计算；写操作不经过展示面；新结构必须经过验收才能上线。

## 2. 现状评估：Livepowers 已实现什么

| 概念 | Livepowers 现状 | 结论 |
|---|---|---|
| 次抛 = System 2 探索 | `explore-with-evidence`；`ontology-grounded-spec` 把"一次性、用完即弃"划为会话层，不写正式规格；每次探索记证据 | **方法已有**，但只产出文本/脚本结果，没有展示面 |
| 固化 = System 1 | `crystallize-to-system1`：F-V-S-R 评分与盈亏平衡 n*、TDD、能力包、独立验收、`lp registry add`；"关键计算不得调用大模型" | **已实现**（流程与 CLI） |
| 计算器结构的经济学 | `docs/paradigm.md` 的反转双系统（CPU vs GPU）与 n* 公式 | **已实现**（论述与 `lp score`） |
| 新表结构 / 新指标 | `ontology-evolution` 提本体 Delta、升版本；本体运行面含规范表与视图 | **部分**：能定义新对象与口径，但不生成、不迁移、不物化表结构 |
| 以新看板形式上线 | `crystallize-to-system1` 写"以新看板的形式上线"；`lp registry add --kind view`；能力包有 `ui:` 字段 | **仅占位**：`ui:` 是自由文本，没有格式、校验和渲染 |
| 固定展示页 + 页面上的智能体 | 无。Livepowers 是给编码智能体用的技能包与 `lp` 命令，没有应用运行时 | **未实现** |
| 次抛结果"一键转固化" | 无。固化候选只来自证据频次（`lp candidates`），终端用户不能从一次分析结果直接发起 | **未实现** |
| 次抛与固化结果的可信度区分 | 无 | **未实现** |

**结论：理念与固化流水线已具备（约一半），"生长面"本身未实现**。缺的是：展示面协议、次抛到固化的晋升通道、表结构的生成与物化、固定页目录，以及一个可演示的参考宿主。

## 3. 目标与非目标

### 目标

- G1 次抛展示：智能体能在业务应用里产出一次性分析展示，**数字全部来自只读的确定性查询**，并明确标为"次抛"。
- G2 语义生长：用户可把一次次抛结果"申请固化"；智能体生成新结构的代码（派生视图/物化表 DDL、指标定义、图表描述、测试），走现有验收门禁后注册为固化结构并出现在固定页里。
- G3 三类需求并存：同一入口先查固化（System 1 命中直接出页），未命中再次抛（System 2），高频次抛自动进入固化候选。
- G4 可审计：每个展示面都能追溯到查询、本体版本、能力版本与生成/采纳记录。

### 非目标

- 不做通用对话产品，不托管模型，不做模型路由。
- 不在客户端执行智能体生成的代码；展示面只传数据与组件描述。
- 不经展示面执行写操作（写操作仍走 `oltp-action-safety`）。
- 不实现完整的 A2UI 渲染器，只实现业务分析常用的组件子集。
- Livepowers 本体仍保持零依赖（Python 标准库）；参考宿主同样零依赖。

## 4. 三类需求与生命周期

```
用户在业务应用里提问
  └─ lp registry find（System 1）
       ├─ HIT  → 固定页 / 固化结构直接计算出结果（CPU，确定）
       └─ MISS → 智能体次抛分析（System 2，只读查询）→ 次抛展示面（标"次抛"）
                   ├─ 用完即弃（记证据）
                   └─ 用户"申请固化" 或 同意图证据达到候选门槛
                        → 生成新结构：本体 Delta + 视图/物化表 DDL + 指标 + 展示面描述 + 测试
                        → 孪生环境复算，与次抛结果逐项对账
                        → acceptance-gates（生成者 ≠ 采纳人）
                        → 生产迁移（带回滚脚本），核验结构存在并留部署回执
                        → 注册为固化结构，出现在固定页目录
运行期：口径变化 / 环境漂移 / 连续失败 → 去固化，回到次抛
```

| 类别 | 载体 | 计算方式 | 可信度标识 | 生命周期 |
|---|---|---|---|---|
| 存量固化 | 固定页 + 已注册能力 | CPU 确定计算 | "固化 vX.Y，本体 vA.B" | 长期，按版本演进 |
| 新增固化 | 新生成的结构，经验收后注册 | CPU 确定计算 | 同上，并标"新增于某日" | 同上 |
| 次抛 | 次抛展示面 | 模型编排只读查询，数字由数据库算出 | "次抛，未经验收" | 会话内，留证据 |

## 5. 功能需求

### F1 展示面描述（Surface）格式

- 新增 `templates/surface.json`：声明式的展示面描述，**与 A2UI 的结构对齐**（界面结构与数据模型分离，按组件类型渲染），先支持组件子集：KPI 卡片、表格、柱状图、折线图、筛选器。
- 每个展示面必须声明：
  - `tier`：`fixed` / `ephemeral`
  - `data`：数据来源。只能引用本体中的规范表、视图或已注册能力，并附上查询文本与参数
  - `provenance`：本体版本、能力 id 与版本（固化时）、生成者、生成时间
- 展示面里**不允许出现可执行代码**，只有数据与组件描述。

### F2 `lp surface` 命令

- `lp surface validate <file>`：校验格式、组件类型，以及数据引用是否都在本体内；次抛展示面不得引用写操作能力。
- `lp surface record <file> --intent <意图>`：记录一次次抛展示，自动写一条 S2 证据（复用 `lp evidence add`）。**只记元数据，不记结果数据**：展示面结构、查询文本与参数、本体版本、结果行数与结果摘要哈希（以及对账要用的少量汇总值，如合计数）。元数据存在 `.livepowers/surfaces/ephemeral/`，会随项目进 git，所以绝不能写入明细行或敏感字段值。
- `lp surface promote <file> --by <申请人>`：把一次次抛展示申请固化，生成看板任务（`lp task new`）并登记为固化候选，引用上面那份元数据。对账时按记录的查询与参数**重新执行**得到基准结果，不依赖保存下来的明细。
- 次抛的结果明细只在会话内使用。如果宿主需要缓存，放进不进 git 的目录（`lp init` 生成的 `.livepowers/.gitignore` 要排除 `cache/`），并设保留期限（默认会话结束即删）。

### F3 语义生成新结构

在新技能（暂名 `living-surface`）中规定生成步骤，复用现有技能：

1. `ontology-grounded-spec`：把次抛的语义写成规格，确认口径、粒度、维度。
2. 需要新对象或新指标时走 `ontology-evolution`，产出本体 Delta。
3. 智能体生成：派生视图或物化表的 DDL、刷新计划、指标计算代码、固定页的展示面描述（`tier: fixed`）、测试。
4. 在孪生或隔离环境执行 DDL，**用新结构复算，与次抛结果逐项对账**，差异必须解释。
5. `acceptance-gates` 四道门，由与生成者不同的人采纳。
6. **生产迁移**：采纳后，按变更窗口在生产环境执行 DDL；必须同时提供回滚脚本。执行后核验结构确实存在，用同一查询抽样复算，留下部署回执（执行时间、执行者、目标环境、核验结果）。迁移或核验失败就回滚，不进入下一步。
7. 注册：`lp registry add --kind view --package <能力包>`。`lp registry add` 只登记信息，不会建表或建视图，所以必须在第 6 步回执核验通过之后才执行。

能力包字段：沿用现有的 `ui:` 作为展示面描述文件路径（唯一字段，不另设 `surface`）；新增 `ddl`（迁移脚本）、`rollback`（回滚脚本）、`materialization`（`view` / `table` / `incremental`）、`deployment`（部署回执路径）。`refresh` 沿用现有字段。

### F4 固定页目录

- `lp pages list`：从注册表列出所有 `ui:` 指向展示面、且部署回执核验通过的固化能力，作为宿主的固定页目录（JSON 输出）。没有回执的能力不出现在目录里。
- 退役或去固化的能力自动从目录中下线；新版本上线时保留旧版本，供调用方迁移。

### F5 参考宿主（演示用）

- `examples/living_app/`：零依赖演示应用，Python `http.server` 加原生 JS。
  - 左侧是固定页目录（读 `lp pages list`）。
  - 右侧是智能体面板：调用 `lp registry find`，命中则打开固定页；未命中时展示一份预置的次抛展示面（演示中不调用真实模型）。
  - "申请固化"按钮调用 `lp surface promote`。
  - 用 `examples/make_demo_db.py` 的示例库演示完整流程：次抛 → 申请固化 → 生成视图 → 对账 → 采纳 → 出现在固定页。
- 前端只渲染展示面描述，不执行任何来自智能体的代码。

### F6 技能与路由

- 新技能 `living-surface`：何时生成次抛展示、何时建议固化、展示面的安全约束。
- 写进 `using-livepowers` 路由表与 README 技能表。
- `system1-first` 补一句：命中的能力带展示面时，直接打开固定页。

## 6. 准确性、安全性与确定性要求

| 要求 | 做法 |
|---|---|
| 数字可追溯 | 展示面中的每个数都来自有查询文本的确定性计算；模型只负责编排查询和选择组件，不"写"数字 |
| 次抛只读 | 次抛使用只读数据库角色；`lp surface validate` 拒绝引用写操作能力的次抛展示面 |
| 写操作隔离 | 展示面不承载任何写操作；业务操作走 `oltp-action-safety` 的确认点与幂等键 |
| 生成代码不直接上线 | 生成的 DDL 和代码先进孪生环境，过 `acceptance-gates`，由与生成者不同的人采纳；再经带回滚的生产迁移、核验回执通过后才注册 |
| 次抛数据不留痕 | 进 git 的只有展示面元数据（查询、参数、行数、哈希、少量汇总）；明细只在会话内或不进 git 的缓存里，到期删除 |
| 可信度可见 | 次抛与固化在界面上区别展示，次抛不能被当作正式口径引用或导出为正式报表 |
| 无代码跨边界 | 展示面只含数据和组件描述，客户端不执行智能体产出的代码（与 A2UI 的安全取向一致） |
| 去固化 | 口径变化、环境漂移、连续失败时自动下线固定页并回到次抛（复用 `lp registry review` 与漂移检测） |

## 7. 度量

- 请求分布：固化命中率（System 1）与次抛占比，按周看趋势。
- 生长速度：新增固化结构数；从第一次次抛到上线固化的平均时长。
- 准确性：固化结构与次抛结果的对账差异率；上线后失败与去固化次数。
- 经济性：单次请求平均成本（固化 vs 次抛），沿用 `outcome-ledger`。

## 8. 验收标准

1. `lp surface validate` 能拒绝以下情况：含可执行代码、引用本体外对象、次抛引用写操作能力。有单元测试覆盖。
2. `lp surface record` 写出 S2 证据，且落盘的元数据里不含结果明细（有测试断言）；`lp surface promote` 生成看板任务与固化候选。有单元测试覆盖。
3. 在演示库上跑通完整流程：一次次抛分析 → 申请固化 → 生成视图 DDL 与固定页展示面 → 复算对账一致 → 采纳 → 演示库迁移并核验回执 → 注册 → `lp pages list` 出现新页（无回执时不出现，有测试断言） → 再次提问直接 System 1 命中。写成 `examples/walkthrough.sh` 的一段，CI 可跑。
4. 参考宿主在浏览器中能展示固定页、次抛面板、"申请固化"按钮，并清楚区分两种可信度标识。
5. 全部新代码只用 Python 标准库与原生 JS；`python -m unittest discover -s tests -v` 通过。
6. 新技能已加入 `using-livepowers` 路由表与 README 技能表；不含具体组织、人员、客户或项目名称。

## 10. 待决问题

1. 展示面格式是直接采用 A2UI 的某个版本（目前有 v0.8 与 v0.9 两种说法），还是先定义兼容子集、以后再对齐？建议先定义子集，并在文档里写明映射关系。
2. 新结构默认用视图还是物化表？建议按数据量与刷新频率决定，在规格里写明，并由 n* 计算辅助判断。
3. 谁有权采纳"申请固化"？业务负责人、数据负责人，还是两者都要？
4. 次抛结果能否导出？若允许，导出文件必须带"次抛，未经验收"标记。
5. 多租户：新增固化结构是客户级扩展还是领域共性？沿用能力包的 `scope` 字段（`domain` / `client` / `config`）以及资产四道门。
