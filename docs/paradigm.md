# 活产品范式：一页纸

## 两种"死"

- **死代码**：业务含义写死在程序里，交付即冻结；每次变化都要重新解释需求、改写实现。用 AI 更快地生成这种软件，只是穿新鞋走老路。
- **死循环的智能体**：每次都从零理解、从零推理；同一件事做一千次就付一千次推理的钱，结果还是概率性的。

## 一个定义

**Agentic AI = Agent + Ontology + Harness**

| 组成 | 职责 | "活"在哪里 |
|---|---|---|
| Agent | 理解意图、感知环境、规划行动、构建新能力 | 能面对没预见的问题，并把探索成果沉淀为确定性行动 |
| Ontology | 描述面（对象、关系、状态、指标、规则、权限）+ 运行面（规范表、视图、原子行动、审计） | 业务含义独立于代码，可确认、可版本化、随业务演进 |
| Harness | 规格编译、孪生生成、场景预演、操作守护、证据沉淀；四道质量门禁 | 每一次变化都在验证、授权与回撤的保护之下 |

## 反转的双系统

| | System 1：执行者 | System 2：探索者 |
|---|---|---|
| 载体 | 固化的代码、CLI、SQL、工作流 | Agent + 大模型推理 |
| 算力 | CPU | GPU |
| 性质 | 确定、可测试、可审计 | 概率、灵活、能处理新问题 |
| 单次成本 | 趋近于零 | 高 |
| 失败方式 | 显式报错 | 貌似合理的错误 |

默认先走 System 1；不能处理再交给 System 2，并把满足判据的成功路径固化回 System 1。固化失效时，再交还 System 2 去固化。两边不是谁替代谁，而是相互转化。

## 固化的经济学

```
固化值得  ⇔  n > n* = (K + M) / (c2′ − c1)，   c2′ = c2/p + (1 − p)·h/p
```

- 成功率越低，越值得固化。
- 夜间空闲算力能摊薄固化成本 K。
- 口径常变，维护成本 M 就高，这类路径应留在 System 2。

## 一天的节律

| 时段 | 发生什么 |
|---|---|
| 白天 | 能复用的走 System 1；不能的由 Agent 探索，经样例核对后交付，并留下证据 |
| 傍晚 | 把长程任务拆成 DAG，按模型可稳定时长切段，填作业契约，设止损 |
| 夜间 | 长程任务运行；固化评审生成草稿与测试；扫描漂移；复核能力；跑金丝雀 |
| 早晨 | 人工采纳：通过的注册为新 System 1 能力，不通过的写明原因 |

## 交付：先白盒，再契约，后证据闭环

1. **先白盒**：把交付拆成可见步骤，标注对象、状态、产物和责任主体。
2. **再契约**：关键语义、不变量、权限和完成标准做成版本化约定，接入自动检查。
3. **后证据闭环**：独立审查与业务采纳；运行反馈回写本体、契约、工具、Skill 与场景集。

每次现场交付都有两种产出：给客户的**功能**，和回流给产品的**资产**。衡量模式是否跑通，就看第十个同类客户是否比第一个更快、更便宜、更可信。

## 现场交付节奏与警示

- **现场嵌入是"脚手架"不是"房子"**：设限时冲刺的上线目标，控制人力投入与收入的比例上限，每个周期把现场定制回收为可复用的配置与模板；产品平台把 FDE 当作"第二用户"。
- **警示信号**：功能生成很快，但本体映射反复返工、交易行为难以复核；或第十个同类客户仍需要和第一个一样多的人月——都说明还没有形成可规模化的交付能力。

## 局限

- 自动固化并非平凡问题，必须设置证据门槛并由人审核。
- 从运行证据到本体演进之间存在语义鸿沟，本体级变化应由人主导。
- 推理成本继续下降会推高 n*，部分固化将不再必要；但确定性与可审计性在交易类场景中仍然成立。
- 业务高度不确定、本体无法稳定的场景，应停留在 System 2 与会话级。
