# PRD-482/T1：livepowers 技能包评估设计草稿

> 对应 trend issue：zhanglunet/trend#2330。状态：设计草稿，只开 PR 不合并，等用户 review。
> 日期：2026-11-17。来源：PRD-482（2026-11-16 日报，用户 2026-11-17 逐条拍板采纳）。
> 注意：livepowers main 目前基线红（PRD-446 T1 #202 是红的）。本 T1 只做设计，T1 PR 的 CI 可能因此变红——这是基线问题不是设计问题，如实记录，不修 main 基线；T2+ 等基线修好再动。

## 目标

给 livepowers 的技能库配一套包级评估，定期回答“这包技能还管用吗”：质量门 → 语义重叠检测 → 合成评测集 → 实测。评估结果落账，过期 / 重叠 / 失效的技能进整改清单，不直接删。上架审批只收评估过关的技能。

## 一、质量门：技能是否真改变生成行为

- **判定口径**：同一批生成任务，对照组（不用该技能）与实验组（用该技能）各跑一遍，比较生成错误率（错格式、错调用、漏步骤、产出不可用）与返工次数。技能通过当且仅当错误率下降且不引入新类型错误。
- **阈值（草稿，T1 评审定、实测后复核）**：错误率相对下降 ≥ 20%，且新增错误类型为 0；样本量每技能 ≥ 20 个任务，低于样本量不判通过、判“证据不足”。
- **判定流程**：三档——通过 / 整改（进清单，限期复测）/ 证据不足；阈值放在评估配置文件中，改阈值要留评审记录。
- **防拍脑袋**：阈值初值由 T1 设计评审定；T2 实测跑完后复核一次，偏离过大则调阈值并记录理由，不静默改数。

## 二、重叠检测：库里技能别重复

- **方法**：两层。① 文本层：技能说明与步骤的语义相似度（嵌入向量余弦），相似度 ≥ 0.8 标为“疑似重叠”；② 行为层：同一任务分别只启用其中一个技能，看产出是否实质相同（生成结果、关键步骤、调用序列一致），行为一致才判“确认重叠”。
- **处置**：疑似重叠只进待核查清单，不自动合并；确认重叠进整改清单，由人决定合并、拆分或保留分工（保留须写明分工理由）。
- **覆盖**：全库技能两两比对，新增技能上架前先跑重叠检测，结果附在上架评审材料里。

## 三、合成评测集：造题考技能

- **题源**：题必须源自真实案例——历史生成任务、真实用户需求、已知的生成失败案例改编（Claude-BugHunter 式证据来源）。每道题记录来源（任务 / 案例编号）、考察的技能点、预期产出要点与判定标准。
- **证据要求**：无来源的题不进评测集；预期产出要点须有人工核对或可复核的依据（对照历史生成记录）。
- **题集管理**：题集分版本管理，新增 / 修改题要留变更记录；定期轮换一部分题，防止技能只针对题集调优。
- **覆盖**：每技能至少 5 道题，覆盖其宣称的核心能力；高风险技能（错了会拖垮整库口碑）优先补题。

## 四、实测：跑真实生成任务量行为变化

- **方案**：取真实生成任务样本（脱敏后），分启用 / 不启用技能两组跑，度量：① 行为变化——生成错误率、返工次数、人工修正量；② 效率变化——任务耗时、来回问答轮数；③ 行为是否按技能走——关键步骤执行率（如先读技能说明、再按步骤生成）。
- **度量口径**：行为变化以“错误率相对变化 + 返工次数变化”为主指标，耗时为辅；只看一次跑分不判，同一任务集跑两遍取稳定值。
- **报告**：每次实测产出评估报告落账（日期、任务集版本、技能版本、指标、结论），报告与技能版本绑定，技能改了要重跑相关部分。

## 五、评估结果落账与整改清单

- **落账**：每次评估都产出带时间戳的报告，存评估记录目录，与技能版本、题集版本绑定，可复核。
- **整改清单**：过期（上游变了，如插件接口 / 工具变了）、重叠、失效的技能进清单，清单 append-only（只追加、不改历史条目），每条记原因、证据、整改期限、复测结果。
- **不直接删**：评估结论只进整改清单；技能下线另走审批，绝不因评估未过关直接删技能或改技能库。
