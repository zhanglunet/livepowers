## 2. 计数方法与局限

近似法（`token_compare.py::count_tokens`）：
- CJK 字符（含汉字、全角标点）= 1 token/字；
- 其余非空白字符 = 0.25 token/字；
- 空白字符不计。

**局限（诚实声明）：**
1. 绝对数值是近似：与真实分词器（如 tiktoken，按 BPE 切分）会有偏差，尤其英文长词/代码标识符的切分方式不同。
2. 但同一方法作用于改造前后两边，**降幅比值可比**——结论看的是"省了百分之几"，不是绝对 token 数。
3. 场景 3 的简洁侧用 `pty` 模块模拟 tty（摘要行只在 tty 下生效，管道/重定向时原文不动是设计如此）；两边都做了 `\r\n` 归一化，比较公平。
4. 输入 token 未单独列：命令本身改造前后一字不差，输入侧无变化。

## 4. 降本不明显的分析与做/不做结论

### 场景 1：registry review（降幅 3%）——接受现状，不做

原因：6 项刚过折叠阈值（>5），只折叠掉 1 项；而简洁版新增的结论行（`复核完成：6 项待处理`）本身是规范要求的"结论先行"，吃掉了一部分节省。这是阈值设计的固有形态：**刚过线时收益最小，条目越多收益越大**（20 项时约省 60%）。
结论：不做。结论行的信息价值（用户一眼看到待处理数）超过 token 成本；且"可预测的长度上限"本身就是折叠要保证的。

### 场景 5：scan --diff（-24%，反而变多）——接受现状，不做

原因：折叠提示行（`…共 6 项，已折叠（LIVEPOWERS_VERBOSE=1 显示全部）`，约 18 token，
CJK 密集 + 必须写明的开关名）比被折叠掉的那 1 行短文本（约 7 token）更贵。
这是真实的边际效应：**变更数 n≤7 时提示行成本超过折叠收益，n≥8 才回本**。
结论：不做。理由有三：
1. 真实场景中漂移要么 0 项（单行"无漂移"，无折叠），要么大批变更（收益显著）；6–7 项的边际情形少见；
2. 提示行必须写明开关名以保证可发现性（T3 测试还专门断言了这一点），缩短空间有限；
3. 折叠的核心价值是"长度上限可预测"，不是逐 token 最优。
未来可选优化（不属本次范围）：把提示语缩短为 `…等 N 项（LIVEPOWERS_VERBOSE=1 展开）`，可省约 6 token/次。

### 其他场景

- score（20%）、evidence stats（46%）：收益符合预期，接受现状。
- scan 指纹（97%）：P0 场景大胜，188 行 YAML → 1 行摘要，正是 T2 清单里标注"人读费力"的痛点。接受现状。

## 5. 总体结论

- 5 场景合计 **1063 → 350 token，降幅 67%**。大头来自 scan 指纹（P0 高收益场景），符合 T2 清单的优先级判断（P0 先做）。
- 两个"降本不明显"的场景都属阈值边际效应，已逐项分析，结论都是**接受现状、不做进一步压缩**。
- 回归安全：`--json`、hook 协议、退出码（score 的 0、drift 的 5）等机器可读部分逐字节不动（T3 已测，本次抽查 exit 码一致）。
