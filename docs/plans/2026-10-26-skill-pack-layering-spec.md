## 1. 总则

### 1.1 目的

技能库（skill library）长大后会出现两个问题：整包太大装不下、skill 多了找不到。
本规范给所有采用「技能库 → sub-pack → skill」三层组织的仓库定一套共同口径：
按什么维度分包、包怎么划、总登记册至少登记什么、名字和版本怎么管。
任一仓库按本规范对齐后，其技能包应做到：可按包独立安装、可按触发词检索、
可被其他仓库按版本号引用本规范做同构适配。

### 1.2 适用对象与术语

- **技能库（library）**：一个独立发行的仓库，含一个或多个 sub-pack。
- **sub-pack（分包/包）**：技能库内的发行与安装单位，含一到多个 skill。
- **skill**：最小能力单位，有且只有一个归属包（§2.1）。
- **总登记册（registry）**：一仓一份的机器可读清单，登记全部包与 skill（§4）。
- **适配仓**：引用本规范做分层适配的其他仓库；源头仓即维护本规范的仓库。
- 规范用语：**必须 / 不得**为硬性条款；**应**为默认要求，偏离须在登记册或适配
  文档中注明理由；**可**为可选。

### 1.3 本规范不管什么

- 不管 skill 的功能内容与质量标准（各仓自理）。
- 不管发布到哪些工具/运行时（发布矩阵另有口径，如 PRD-130）。
- 不管 skill 自身元数据的字段标准（如 SKILL.md frontmatter，另有口径，
  如 PRD-199）；本规范只在 §4.4 约定二者的衔接。

## 2. 分层维度

### 2.1 主维度（归属维度，唯一）：职能领域

sub-pack 按**职能领域**划分：一个 skill 解决哪一类问题，它就归哪个包。
每个 skill 有且只有一个归属包；归属记在总登记册里，是单一事实源（§7）。

选领域作主维度的理由：

- 安装以包为单位，用户的安装决策是按领域做的（「我要交付类能力」）；
- 领域边界是所有维度里变化最慢的，按它归属，skill 不需要频繁搬家；
- 领域与触发场景直接对应，检索（按触发词找 skill）天然按领域收敛。

### 2.2 辅助维度：只做视图，不做归属

以下维度**不得**用作归属划分，只能作为登记册字段或登记册的投影视图：

| 维度 | 在本规范中的位置 | 理由 |
|---|---|---|
| 使用阶段（入口/探索/固化/验收/复盘…） | 登记册可选字段 `stage`，可投影成阶段视图 | 阶段是使用顺序，不是所有权；同一 skill 常跨阶段出现 |
| 受众角色（岗位/人群） | 登记册可选字段 `roles`，可投影成角色选配包 | 角色包是「按人选配」的组合视图，skill 本身不属于某个角色 |
| 运行通道（哪种 agent 工具/运行时） | 不进登记册归属，归发布矩阵管 | 同一 skill 发到多通道是分发问题，不是分层问题 |
| 成熟度（稳定/实验/弃用） | 登记册可选字段 `status` | 状态会变，归属不应随状态变 |

视图可以有多个，但视图不产生第二份归属、也不复制 skill 本体（§3.3 单一事实源）。

## 3. sub-pack 划分原则

### 3.1 规模

- 一个包**建议**含 2–8 个 skill。
- 只有 1 个 skill 独成一包，仅当：该领域明确会继续扩展（在该包一句话定位中
  说明方向），或有隔离需要（高风险、强外部依赖）。其余情况并入相近领域包。
- 超过 8 个**应**评估按子领域拆包：拆分点仍按 §2.1 的职能领域细分，
  不按阶段或角色拆。

### 3.2 内聚

- 同包 skill 应共享同一领域的问题域与用户意图。判定问题：
  「用户会不会把它们当一类能力、愿意一起装？」答否，就不应同包。
- skill 归属判定顺序：① 主要触发场景属哪个领域 → ② 主要产物属哪个领域 →
  ③ 仍冲突时，看它依赖最多的同域 skill 在哪个包。

### 3.3 跨包引用

- skill **可以**调用或引用其他包的 skill，但**必须**在登记册中用可选字段
  `depends_on` 声明（包级依赖随 skill 级声明成立）。
- **禁止隐式依赖**：一个包的安装与使用说明不得默认另一个未声明依赖的包已安装。
- **单一事实源**：一个 skill 在库内只有一个权威副本。发行形态需要它出现在
  多处时（如多个工具的目录），副本必须与权威源逐字节一致，并由自动检查守护；
  不得在副本上分头修改。
- 包级依赖**不得成环**。成环说明领域边界划错了：先调整划分，再谈实现。

### 3.4 包的独立性

每个 sub-pack 应可独立安装、独立卸载；卸载一个包不得破坏其他包已声明的功能
（已声明的依赖链除外，卸载时应提示依赖方）。

## 4. 总登记册

### 4.1 形态

- 一仓一份。机器可读格式（JSON 或 YAML）为权威源；人类可读表格应由其生成，
  或与之保持同步（不一致即漂移，见 §7）。
- 登记册文件应放在仓库根目录或 `docs/` 下可发现的位置，并在 README 中链接。
- 结构：登记册由「包条目」数组构成；每个包条目内嵌其「skill 条目」数组。

### 4.2 必填字段（共 7 个，从严定义，不随各仓增减）

包条目（5 个）：

| 字段 | 含义 | 约束 |
|---|---|---|
| `name` | 包名 | 符合 §5.1，全库唯一 |
| `positioning` | 一句话定位 | 一句话说清「给谁、解决什么」，建议 ≤60 字；双语仓可同一字段双语并存 |
| `version` | 包版本 | semver，见 §6.3 |
| `spec_version` | 本条目遵循的本规范版本 | 如 `1.0.0`，见 §6.1 |
| `skills` | skill 条目数组 | 非空，见下 |

skill 条目（2 个）：

| 字段 | 含义 | 约束 |
|---|---|---|
| `name` | skill 名 | 符合 §5.2，全库唯一（不靠包名消歧） |
| `triggers` | 触发词/触发描述 | 数组或一句话；写「用户说什么时该 skill 应被触发」，是登记册可检索的依据 |

### 4.3 可选字段（推荐集）与扩展规则

推荐可选字段（包与 skill 条目通用，按适用选用）：`description`（长描述）、
`keywords`、`stage`（§2.2）、`roles`（§2.2）、`depends_on`（§3.3）、
`status`（`stable` / `experimental` / `deprecated`）、`license`、`homepage`、
`examples`（验收例或示例的链接）。

扩展规则（防止规范写得过重、各仓跟不动）：

- 各仓**可**加自定义字段，一律以 `x-` 前缀命名（如 `x-owner-team`）。
- 消费工具**必须**忽略不认识的字段（含 `x-` 字段与未来新增的可选字段），
  不得因未知字段报错。
- 可选字段升为必填只能走规范 MAJOR 升级（§6.1），不得由单个适配仓自行宣布。

### 4.4 与 skill 自身元数据的衔接

skill 条目的 `name` / `triggers` 应与 skill 自身声明的元数据
（如 SKILL.md frontmatter 中的名称与触发描述）保持一致。
两者不一致即漂移（§7）；以何者为生成源由各仓自定，但不得长期双轨维护。

### 4.5 最小示例（结构示意）

```yaml
registry:
  - name: <library>-<domain>        # 包名，见 §5.1
    positioning: <一句话定位>
    version: 0.1.0
    spec_version: "1.0.0"
    skills:
      - name: <skill-name>
        triggers: ["<触发词1>", "<触发词2>"]
      - name: <another-skill-name>
        triggers: "<一句话触发描述>"
```

## 5. 命名规则

### 5.1 sub-pack 名

- 格式：`<库前缀>-<领域词>`，全小写 kebab-case。库前缀为技能库名
  （如 `livepowers-core`）；无品牌前缀的库可直接用领域词，
  但同一库内风格必须一致。
- 领域词用单个领域名词或短语，不用阶段词、角色词（那是视图维度，§2.2）。

### 5.2 skill 名

- 全小写 kebab-case，动词短语或名词短语，与库内既有风格保持一致。
- **全库唯一**：不得靠所属包消歧同名。
- 不得含版本号；不得含所属包名（改归属不改名）。
- 语义相近的 skill 名应可直接区分，禁止仅靠序号或 `-new` 之类后缀区分。

### 5.3 改名

包名与 skill 名一经发布即是标识符。改名是破坏性变更：按 §6 走 MAJOR，
并在该仓的适配/迁移文档中给出旧名 → 新名对照与迁移说明。
日常迭代只改定位文案，不改名。

## 6. 版本规则

### 6.1 本规范的版本

本规范用 semver 管理，适配仓引用的就是这个版本号：

| 变更 | 级别 | 对适配仓的影响 |
|---|---|---|
| 必填字段增删、字段语义变更、硬性条款变更 | MAJOR | 必须重新对齐，并更新登记册 `spec_version` |
| 新增可选字段、新增建议性条款、扩充示例 | MINOR | 向后兼容，按需跟进 |
| 文字澄清、错别字、排版 | PATCH | 无语义影响 |

### 6.2 谁能改规范

- 本规范由源头仓维护（本文件所在仓库），修订走源头仓的 PR + 评审流程。
- 适配仓以引用版本号的方式跟随，**不**在自己仓库里改规范正文；
  有异议向源头仓提 issue，达成一致后由源头仓发新版本，
  各适配仓再按自己的节奏升级所引版本与登记册 `spec_version`。
- 规范的版本历史在本文件 §8 维护。

### 6.3 包与 skill 的版本

- 每个 sub-pack 独立使用 semver：包内 skill 增删或定位变更至少升 MINOR；
  skill 归属迁出/迁入、包改名升 MAJOR；仅文案修订可升 PATCH。
- 整库统一版本（lockstep，全库同号）是**允许的本地政策**，但不是本规范要求；
  采用与否由各仓在适配文档中声明。
- skill 默认随包版本走；若运行环境要求 skill 自带版本，按其要求填写，
  与包版本不一致时在登记册可选字段中注明。

### 6.4 引用与对齐声明

适配仓应在登记册或 README 中写一行对齐声明：

```
技能包分层规范：skill-pack-layering-spec@<版本>
```

评审与校验以所引版本为准；未写明版本视为未对齐。

## 7. 一致性要求（只定口径，工具各仓自理）

- 登记册是包归属与检索的**单一事实源**。目录结构、市场清单、分组展示文件
  与登记册不一致，即为**漂移**；发版前必须消除漂移，或在登记册中登记例外
  及理由。
- 一切视图（阶段视图、角色选配等）必须能从登记册字段投影得出，
  不得与登记册并行维护第二套归属数据。
- 校验脚本与发布门禁的实现不在本规范内，由各仓按本地规范落地
  （如把「登记册 ↔ 目录」一致性纳入发版检查清单）。

## 附录 A：livepowers 映射示例（示例，非规范条文）

本附录示范一个既有技能库如何映射到本规范。仅为示例：本 PR 不据此改动
现有结构，livepowers 的分包与登记册落地归 PRD-227 的 T2/T3，
其他适配仓在各自文档中照此写法给出自己的映射。

### A.1 现有 5 个插件 → 5 个 sub-pack

| sub-pack（现有插件） | 一句话定位（取自各 plugin.json 描述，落地时提炼） | skills 数 | 版本 |
|---|---|---|---|
| `livepowers-core` | 核心工作流：先查固化能力、带证据探索、把验证过的路径固化成可测试能力 | 5 | 1.6.0 |
| `livepowers-ontology` | 本体：环境扫描、知识演进、数字角色规约 | 4 | 1.6.0 |
| `livepowers-delivery` | 交付与安全：独立验收门、现场交付、结果账本、操作安全与可审计通信 | 7 | 1.6.0 |
| `livepowers-night` | 夜间循环：夜间计划与晨间固化评审 | 2 | 1.6.0 |
| `livepowers-tooling` | 工具：agent harness 与 skill 编写指南 | 3 | 1.6.0 |

合计 21 个 skill；现行版本政策为全库 lockstep（5 包同为 1.6.0），
属 §6.3 允许的本地政策。

### A.2 从映射看到的现状与差距（供 T2/T3 参考，本 PR 不处理）

- 现有领域划分（工作流核心 / 本体 / 交付与安全 / 夜间循环 / 工具）符合 §2.1
  主维度；各 plugin.json 的描述即 `positioning` 的雏形，T2 提炼为一句话定位
  并写入登记册。
- 现状有三处「登记面」（marketplace 清单、skills.sh 分组文件、README 技能表），
  尚无 §4 意义上的单一登记册；T3 按 §4 收敛为一份权威登记册，
  其余降为由登记册生成或投影的视图。
- 示例性漂移：分组展示文件里 Delivery 组列了 6 个 skill，而该包实际含 7 个
  （多出的一个未进分组）——即 §7 所称漂移，T2/T3 消除。
- README 技能表按阶段分组（入口 / 本体 / System 1 / 固化 / 验收…），与包归属
  并不一致（如某 skill 归属 ontology 包、在表中列于「价值」组）——按 §2.2
  这是阶段视图，T2 起应改为由登记册 `stage` 字段投影，不再手工维护第二套归属。
- 仓库已有的按岗位选配的角色包（role-packs）是 §2.2 的角色视图实现，
  不构成第二层归属，与本规范不冲突。

### A.3 一个包条目的样子（以 night 包为例，triggers 为示意）

```yaml
registry:
  - name: livepowers-night
    positioning: 夜间循环：夜间计划与晨间固化评审
    version: 1.6.0
    spec_version: "1.0.0"
    skills:
      - name: night-loop-planning
        triggers: ["排夜间计划", "夜间循环排程"]
      - name: nightly-crystallization-review
        triggers: ["晨间评审", "夜间产物固化复核"]
```
