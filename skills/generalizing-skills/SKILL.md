# 泛化技能：本体契约 + 方法 + 环境绑定

**一句话：把一份项目专属的 skill 拆成"跨项目不变的业务本体与方法"和"每个 workspace 一次的环境绑定"，换项目只换绑定，规则只有一份真值。**

为什么需要它：没有这个技能时，Agent 也会把路径、列名搬进配置文件，但会把**业务规则**（"只算已签收""退货不进分母"）和**规则取值**（阈值、状态叫法）一起塞进每个项目的配置——于是每个项目各有一份规则真值，口径悄悄分叉；复用时只在"找不到列"时才报警，表头没变而状态值多了一种就会**静默算错**。

## 三层：先分清每一句属于哪层

| 层 | 是什么 | 跨项目 | 放在哪 |
|---|---|---|---|
| **业务本体** | 对象、关系、规则的**模式**（完成率 = 已完成 / 目标；退货不进分母；门店 ∈ 区域） | 相同 | 项目或企业的本体（`ontology/ontology.yaml`），skill 只**引用** |
| **方法** | 步骤、顺序、校验框架、交互协议（先对账再出报表；结构识别不准必须问） | 相同 | `SKILL.md` 与参数化脚本 |
| **环境实例** | 数据源、表与列、规则的**取值**（阈值 0.85、"已签收"在这里叫什么）、模板、交付渠道 | 每个 workspace 一份 | 绑定文件（见下文） |

一句话判据：**这句话里有没有只有某个项目才有的名词或数值？**有 → 环境实例；没有，且描述"业务是什么" → 业务本体；描述"怎么做" → 方法。

**规则模式与规则取值必须分开。**"完成率低于阈值标红"是模式（本体）；"阈值 = 0.85"是取值（绑定）。不分开，就会把 A 项目的口径当成通用规则，或者每个项目各写一遍规则。

## 第 0 步：值不值得泛化

不是所有 skill 都该泛化。泛化本身就是一次固化，按 `crystallize-to-system1` 的思路先过判据：

| 判据 | 泛化 | 不泛化，保持项目专属 |
|---|---|---|
| 同类 skill 数 | 已有 ≥2 份同类（章节骨架几乎一样） | 只此一份 |
| 频率 | 周期性（日报、周报、月报、例行稽核） | 一次性交付、单次外部系统交互 |
| 可验证 | 有对账、合计守恒、与上期对比等自动核对 | 结果只能靠人看 |
| 稳定 | 规则模式稳定，只是取值不同 | 每个项目的做法本身都不一样 |

可验证为 0 的不泛化：泛化后没法证明它在另一个项目是对的。

## 第 1 步：逐句标注，用"变化分层"判断归哪层

在原 `SKILL.md` 和脚本上逐句标三类：【本体】【方法】【实例】。拿不准时，问"换一个项目，这句话会在哪一层变"——沿用 `ontology-grounded-spec` 的变化分层：

| 变化落在 | 归到 |
|---|---|
| 界面（文案、版式） | 环境实例 |
| 参数（阈值、目录、库表、列、渠道） | 环境实例 |
| 功能（逻辑的增删） | 方法 |
| 本体（对象、关系、规则模式） | 业务本体 |
| 会话（只这一次） | 不泛化，删掉 |

脚本里写死的常量（sheet、列字母、阈值、路径、群名）全部是【实例】。

## 第 1.5 步：泛化产物进哪一边

skill 里常常混着两种东西，分开放：

| 内容 | 是什么 | 去处 |
|---|---|---|
| 确定性的计算、查询、填表、对账 | **能力**（工具箱） | 参数化脚本 / CLI / SQL，按 `crystallize-to-system1` 带测试，注册为 `--kind cli` 或 `script` |
| 何时用、按什么顺序、什么时候问人、怎么校验 | **操作手册** | `SKILL.md`，注册为 `--kind skill` |

能写成脚本的判断不要留在手册里让模型每次"想"；需要判断的部分不要硬写进脚本。

## 第 2 步：写本体契约，不复制真值

在泛化后的 `SKILL.md` 里写一段**本体契约**：依赖哪些对象、属性、规则，以及兼容的本体版本。

```yaml
ontology_contract:
  ontology: <本体名>            # 指向项目或企业本体，不在 skill 里另起一套
  version: ">=1.2 <2"
  objects: [Order, Store]
  rules: [R-COMPLETION-RATE, R-RETURN-EXCLUDED]   # 只写规则 ID，规则正文在本体里
```

- 本体里**没有**这条规则 → 走 `ontology-evolution` 提 Delta，不要把规则写进 skill 或绑定里凑合。
- 允许附一段**摘要**方便阅读，但要标明"以本体为准"和摘要对应的版本。
- 还没有正式本体时，用 `env-scan-ontology` 的草稿本体（`0.1.0-draft`）起步，契约照写。

## 第 3 步：定角色

把每个【实例】归到一组角色，**角色而不是具体值**。下面是四组；团队已有"结构 / 语义 / 产物"三组的，可以保留三组，但语义组内部必须按第 1 步拆成"本体规则"和"实例参数"两类——分组数量可以变，模式与取值分开不能变。

| 组 | 角色 | 谁来定 | 初始化时 |
|---|---|---|---|
| **结构** | 数据源、对象与粒度、主键、期间列、维度列、指标列 | 自动识别，带置信度 | 置信度低于阈值**必须问**，不能静默选一个 |
| **本体规则** | 规则模式（来自本体契约） | 本体负责人 | 只核对版本，不逐项重问 |
| **实例参数** | 规则取值：阈值、状态值映射、分母口径参数 | 业务确认 | **必须问**；不得默认继承上一个项目的取值 |
| **产物** | 模板、格式、交付渠道 | 业务确认 | **必须问** |

## 第 4 步：参数化脚本

脚本不再写死任何【实例】，只读绑定；规则模式按本体契约实现，取值从绑定读。

**怎么算做对了：换一份绑定，脚本一行不改也能跑。**只把列名换个地方写死，不算泛化。

## 第 5 步：首次初始化（新 workspace 第一次使用）

skill 要自带一段"初始化"流程，首次使用时执行，**不直接出结果**：

1. **发现环境**：扫描数据源，生成环境指纹。数据库用 `env-scan-ontology` 的扫描脚本；文件类数据源记录文件清单、sheet、表头和关键列的取值枚举。
   ```bash
   python3 <scripts>/scan_sqlite.py <db> --fingerprint .livepowers/env/<skill>-fp.json > /dev/null
   python3 <scripts>/scan_sql.py --dsn <dsn> --fingerprint .livepowers/env/<skill>-fp.json > /dev/null
   ```
2. **映射结构角色**，给出置信度；低于阈值的逐项问。
3. **核对本体契约**：项目本体版本是否落在契约范围内；不在就停下。
4. **确认实例参数和产物**：逐项问业务，把枚举值摆出来让对方选（"状态列里有 已签收 / 部分签收 / 已取消，计入哪些？"）。
5. **试跑**：用样例数据 dry-run，过 skill 自己的校验框架（合计守恒、与上期对比），请业务核对。
6. **写绑定**，入 git。位置可以按团队约定（如 `.skill-init/<能力名>.yaml`），默认放 `.livepowers/bindings/`；字段必须齐——本体版本、环境指纹、确认人和确认时间缺一不可，否则无法判断绑定何时失效：

```yaml
# .livepowers/bindings/<skill-name>.yaml
skill: <skill-name>
skill_version: 1.0.0
ontology: {name: <本体名>, version: 1.3.0}
fingerprint: .livepowers/env/<skill-name>-fp.json
structure:                     # 自动识别，带置信度
  source: data/{yyyy}-{mm}订单明细.xlsx
  object: {column: 门店, confidence: 0.96}
  period: {column: 下单日期, granularity: month}
params:                        # 实例参数：规则取值，业务确认
  R-COMPLETION-RATE: {threshold: 0.85}
  R-RETURN-EXCLUDED: {return_values: [退货, 拒收]}
  status_included: [已签收]
output: {template: templates/订单月报.xlsx, formats: [xlsx, pdf], delivery: <渠道>}
confirmed_by: <业务负责人>
confirmed_at: 2026-10-20
```

初始化本身是一次探索：结束时 `lp evidence add --intent "init <skill-name>" --system S2 ...`。

## 第 6 步：复用前先比对

同一 workspace 再次使用时，**先比对再跑**：

```bash
python3 <scripts>/scan_sqlite.py <db> --fingerprint /tmp/fp-now.json > /dev/null
python3 <scripts>/scan_sqlite.py --diff .livepowers/env/<skill-name>-fp.json /tmp/fp-now.json   # 有漂移 exit 5
```

| 比对结果 | 处理 |
|---|---|
| 指纹一致、本体版本在契约范围内 | 直接用绑定运行 |
| 新增列、列改名 | 只重做受影响的结构角色，问一次 |
| 关键列出现新的取值（如新状态） | 停下，问实例参数怎么处理；**不能静默忽略或默认计入** |
| 本体版本越出契约范围 | 停下，走 `ontology-evolution` 或升 skill 版本 |

改完的绑定重新写 `confirmed_by / confirmed_at`。

**运行时再拦一道**：方法里的校验框架加一条覆盖检查——关键列里"既不在计入清单、也不在排除清单"的取值数必须为 0，否则停下。指纹比对挡住运行前的变化，覆盖检查挡住两次扫描之间的变化。

## 第 7 步：验收

按 `acceptance-gates`，泛化的生成者不验收自己。至少三条证据：

1. **原项目回归**：用原项目的绑定跑同一期数据，结果与泛化前一致。
2. **第二个 workspace 跑通**：另一个人在另一个项目的数据上，从初始化走到 dry-run 出结果，**只写绑定，不改代码**。
3. **护栏有效**：结构识别不准会问、对账不平会停、指纹漂移会拦——都有用例。

泛化后反复使用、判据稳定的 skill，注册进能力注册表，之后靠 `system1-first` 先查再建，避免同类 skill 再被重写一份。同一件事的常见说法登记为意图别名，否则换个说法又会被泛化一遍：

```bash
lp registry add --kind skill --name <skill-name> --intents "<规范意图>,<常见说法>" --entry "<skill-name>" \
  --generated-by <泛化者> --accepted-by <验收人>
lp intents alias "<规范意图>" "<另一种说法>"
```

## 反模式

| 反模式 | 为什么错 |
|---|---|
| 把业务规则写进每个项目的配置 | 规则有了多份真值，口径悄悄分叉；规则属于本体，配置里只放取值 |
| 新项目默认继承上一个项目的阈值和状态映射 | 同名指标在不同项目口径可能不同；实例参数必须逐个 workspace 确认 |
| 只把列名从 SKILL.md 搬进配置，脚本还写死 | 换项目照样要改代码，等于没泛化 |
| 结构识别拿不准时挑一个最像的 | 业务只确认口径和产物，结构猜错没人兜底 |
| 复用时只在"找不到列"才报警 | 列都在、取值变了，结果静默出错；要比对指纹 |
| 为了泛化而泛化一次性 skill | 抽象成本收不回来；先过第 0 步的判据 |
| 在 skill 里自带一份完整本体 | 造出第二份业务真值；只引用 + 摘要 |

## 红线

- 泛化后的 `SKILL.md`、`name`、`description` 里不出现任何项目专属的名词、路径、列名、取值、模板名、渠道。
- 实例参数和产物没有业务确认，不出正式结果。
- 指纹漂移或本体版本越界时，不用旧绑定继续跑。
- 规则模式只在本体里改，不在绑定里改。

## 简洁输出规范

人类可读输出遵循三段式：**结论**（一句话，≤50 字）/ **关键信息**（≤5 条，每条 ≤30 字）/ **详情**（折叠，需要时展开）。`--json`、退出码、机器协议逐字节不动。
全量输出：`LIVEPOWERS_VERBOSE=1 <命令>`（临时）；`<LIVEPOWERS_HOME>/config.yaml` 写 `verbose: true`（持久）。

- 初始化结论行：`初始化完成：<skill-name> 已绑定到 <workspace>，待业务确认 N 项`；关键信息列出低置信度的结构角色和待确认的实例参数。
- 复用前比对结论行：`环境一致，可直接运行` 或 `环境漂移：<一句话>，需重新确认 N 项`；漂移明细折叠。
- 泛化汇报：结论（改成了几层、几组角色）/ 关键信息（本体契约引用了哪些规则、哪些取值待确认）/ 详情（逐句标注结果）。
