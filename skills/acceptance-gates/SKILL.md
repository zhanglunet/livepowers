# 验收门禁

**生成的门槛在降低，验收的门槛在抬高。**测试通过只提供限定范围内的证据，并不证明所有情境下都正确。完成与否由验收条件决定，不由生成者的自我声明决定。

## 四道门（依次通过）

| # | 门 | 发现什么 | 由谁执行 | 证据 |
|---|---|---|---|---|
| 1 | **形式检查** | 结构、类型、必填字段、引用的本体版本存在 | 机器（lint、schema 校验；夜间作业契约用 `lp job validate`） | 检查输出 |
| 2 | **契约测试** | 约定行为：验收样例、业务不变量、八项检查（OLTP） | 机器（测试集） | 测试报告 |
| 3 | **独立对抗审查** | 遗漏前提、口径偏差、越权路径、异常路径 | 与生成者分离的审查者 | 反例清单与结论 |
| 4 | **人工采纳** | 业务意义、未被覆盖的风险 | 有权的业务责任人 | 采纳记录（谁、何时、依据） |

## 独立审查怎么做

- **责任分离**：验收标准和基准用例不能由生成方修改。生成方不得通过改基准让错误结果过关。
- **独立输入**：审查者使用独立数据、**保留测试集**和反例；必要时用异构模型、不同上下文。
- **相关错误**：换一个模型不能自动消除相关错误——两个智能体给出一致答案，也可能只是重复了同一个误解。重要判断仍需责任人确认。
- **对抗推演**（可选，适合有利益冲突的决策）：让两个角色在约束下多轮质询同一份材料（如"提出方"与"审核方"），由脚本居中转话并留痕（`auditable-agent-comms`），输出双方都能接受的区间与未解决分歧，再交人评审。
- 代码审查集中在关键事务、安全边界和异常路径。

## 回执，而不是声明

- 执行类 Agent 调用工具后返回**真实执行回执**（工具返回值、事务 ID、产物位置），不是"已完成"。
- 分析类 Agent 交出**可检查的规格**和可复算的结果。
- 声称完成的消息没有回执引用，视为未完成（`agent_switch.py audit` 会列出）。

## 五种职责

| 职责 | 不得做的事 |
|---|---|
| 派工者（定义任务与授权） | 自行扩大授权 |
| 执行者（生成 / 实现） | 降低验收标准以获得通过 |
| 验证者（运行测试、对抗审查） | 与执行者是同一主体 |
| 采纳人（业务责任人） | 在缺少证据时被动签字 |
| 运营者（上线后监测、接管） | 绕过门禁直接热修 |

小团队可以兼任，但**生成、验证、采纳之间必须保持实质性的责任分离**。`lp registry add` 会拒绝 `--generated-by` 与 `--accepted-by` 相同；`lp task move ... registered` 会拒绝执行者本人。

## 门禁力度与风险成正比

- 界面、参数变化：门 1 + 门 2 + 轻量采纳。
- 规则、权限、事务变化：四道门全过，严格回归，责任人授权。
- 新增工具：四道门 + 安全检查 + 注册 + 版本绑定。

## 操作

```bash
lp task move <id> verify --by <执行者> --reason "提交验收" --evidence <产物位置>
# 门 1、门 2 自动化；门 3 由独立审查者执行；门 4 由采纳人确认后：
lp task move <id> registered --by <验证者或采纳人> --reason "四道门通过" --evidence <验收记录>
lp outcome accept --scenario <场景> --task <id> --by <采纳人> [--first]
```

## 一周节奏（常规迭代单元，非统一承诺）

- 周初：确认意图、契约与基准。
- 周中：并行执行能独立开展的任务，自动验证并处理失败。
- 周末：归档证据、组织采纳、回写复盘（本体、契约、Skill、场景集、门禁规则）。

复杂事务与强合规变更采用适合风险的节奏。

## OLAP 交付检查项

隔离验证和客户样例验收逐条记录以下证据；OLTP 使用 `oltp-action-safety` 的八项检查。

| 项 | 检查 |
|---|---|
| 口径 | 指标定义、过滤条件与本体版本一致 |
| 粒度 | 分组与聚合层级一致，无重复汇总 |
| 关联 | 连接键与基数正确，无漏行或倍增 |
| 金额 | 币种、精度、税口径及合计可对账 |
| 权限 | 数据范围和敏感字段符合授权 |
| 时效 | 数据时间、刷新周期与有效期满足契约 |
| 预算 | 查询资源、延迟与成本在约定上限内 |
